# 可选字幕缓冲模式与播放窗口改进方案

日期：2026-09-19  
状态：方案文档，尚未实现或验证性能。  
适用基线：`rust-app` 当前原生 macOS 应用及其共用播放、字幕链路。

## 1. 已确认的需求

用户已满意现有翻译速度，现有播放与字幕方式保持默认。仅当用户希望给处理留出更多时间时，在设置中主动开启“字幕缓冲模式”，选择增加 3、4 或 5 秒缓冲，再同步播放画面、原声和对应翻译字幕。

第二项（全屏与悬浮小窗）用户已确认已有、没有问题，移出本次改动范围。新增第三项底部控件闲置收起、第四项字幕回看侧栏，详见第 10、11 节。

- 默认关闭新增缓冲，保持当前体验；不自动根据电脑性能切换。
- 开启后可选 3、4、5 秒，首次选择默认 3 秒。每次按选定值固定缓冲，不动态在 3～5 秒间漂移，不因字幕未完成而继续增加延迟。
- 设置保存至本机并在下次启动恢复；首次安装仍使用现有默认方式。
- 正常播放期间保持连续；字幕来不及可以晚到，不能为了字幕暂停画面或原声。
- 只播放原声，不生成翻译配音。
- 保留现有中文、英文、双语显示选项；中文翻译是本次主要改善对象。
- 本次仅编写改进文档，不修改程序、不构建、不替换现有安装包。

**所选 3～5 秒的准确含义：应用新增的媒体缓冲目标，不是距现实直播现场仅有 3～5 秒。** 上游编码、HLS 分片发布、网络和播放器本来就有延迟。首次连接、模型下载和网络卡顿也不能承诺在 3 秒内完成。

缓冲只能吸收一定程度的处理延迟和耗时波动，不会提高模型本身的持续处理能力。若电脑长期处理速度低于音频产生速度，5 秒缓冲也无法保证字幕始终跟上；因此保留过期丢弃与落后状态提示。

以下技术方案中的“3 秒”均为选择 3 秒时的示例；实现使用所选缓冲值 D（3、4、5 秒），对应窗口、提示和验收均按 D 计算。默认模式不启用新增缓冲与提前字幕调度。

## 2. 预期观看体验

默认模式沿用现有打开与播放流程。启用字幕缓冲模式后，打开来源显示“正在准备 3 秒播放缓冲…”（数字随选择变化）。音视频接收和可用模型的字幕处理同时开始，缓冲达到条件后，以正常速度播放原声与画面。字幕按照对应媒体时间出现，不提前透露尚未播放的内容。

例如：播放位置为第 10 秒，识别分支可以处理已经收到的第 10～13 秒音频；为第 12 秒准备好的字幕留在队列，到画面播放至对应位置再显示。

这不意味着第 10 秒开始的一句长话在第 10 秒就一定能显示完整译文。成句等待、识别、翻译、排队都会消耗提前量；长句仍需按短语分段。

## 3. 当前代码与缺口

以下为本次直接查看源码得到的现状，不代表新方案已经通过运行验证。

| 位置 | 当前行为 | 改进方向 |
| --- | --- | --- |
| `public/hls-audio.js` | 从 HLS 音频分片解码出带起止时间的 PCM，但 `tick()` 仅输出到 `video.currentTime + 0.1`，暂停时不输出 | 让识别读取游标提前于播放游标；允许启动缓冲阶段处理音频 |
| `public/speech-chunks.js` | 按能量与静音分段；约 0.4 秒静音结束一句，最长 16 秒；满 1 秒后增量输出 | 保留媒体起止时间，增加长句短语切分，不能等待完整长句才翻译 |
| `public/app.js` | 录入字幕任务时使用本机钟表时间；暂停时拒收音频；识别完成立即调用显示；待处理任务超过 3 条丢弃旧项 | 分离缓冲状态与用户暂停，按媒体时间和播放期限调度任务 |
| `public/captions.js` | 英文结果立即覆盖画面，中文跟随最新记录；通过 7 秒墙钟定时清屏 | 结果先进入字幕队列，按播放时间呈现、更新和清除 |
| `public/app.js` 播放配置 | `liveSyncDurationCount: 3` | 这是 3 个分片，不是 3 秒；不能把它直接当作本需求已实现 |
| `src/api.rs` | 识别返回文本 `en`，翻译返回文本 `zh`，未提供词级时间戳 | 首期由请求关联信息保留短语级时间范围，不宣称词级精确同步 |

现有 HLS 分片解码提供了可复用基础，但“把播放器晚启动 3 秒”本身不够：如果识别仍跟随播放游标，就没有给识别争取提前量。

## 4. 推荐处理链路

```text
接收 HLS 音视频分片（保留媒体时间）
  ├─ 播放缓冲 → 到播放时刻 → 同步输出画面和原声
  └─ 音轨解码 → 提前读取 → 语音分段 → 识别 → 翻译
                                              ↓
                                      带时间的字幕队列
                                              ↓
                                根据实际播放位置显示字幕
```

画面和原声继续由同一个播放器同步输出，不单独延迟声音，也不通过外放或系统录音重新采集。字幕调度以播放器的媒体时钟为准，本机钟表只用于诊断处理耗时。

### 4.1 三个位置必须分开

- 播放位置：用户正在观看的媒体时间。
- 已连续接收位置：音视频已经连续可用到哪里，不能用跨越缺口的最远分片代替。
- 识别读取位置：已经送入语音处理的音频末尾，正常目标最多领先播放位置约 3 秒。

首次启动选择与原播放策略一致的起点，积累起点后约 3 秒连续媒体；此期间识别可先处理已到音频。满足媒体缓冲条件就开始播放，不等待译文。对于录播，同样可先读后播，启用该模式时采用所选处理窗口，不预处理整部视频。

直播正常播放时检查现有自动追赶直播逻辑，避免其跳转或加速吞掉新增缓冲。不要每隔几秒强制回跳来“修正”延迟。稳定网络下维持目标，网络饥饿时仍可能卡顿，字幕功能不能保证消除媒体本身的卡顿。

### 4.2 分段与翻译

优先在静音、标点或稳定短语边界完成一段；连续讲话时必须有短语长度上限，不能沿用最长 16 秒作为唯一结束条件。首轮实验可从约 1～2 秒短语窗口开始，具体数值由真实语音的完整性与耗时决定，暂不写死为性能保证。

未展示的识别、翻译结果可以被更完整的版本替换；已经展示的字幕只允许同一短语的受控校正，避免逐字闪动。上下文可以辅助翻译，但当前字幕不得带入尚未播放的后续短语。没有词级时间戳时，这属于短语级同步，精细对齐是后续独立改进。

总预算包括：等待分段、音频解码、任务排队、识别、翻译和调度。必须测量端到端预算，不能用单次模型推理耗时证明整条链路在 3 秒内完成。

### 4.3 字幕记录与显示

每条记录至少关联：播放会话、时间线代次、短语 ID、版本、媒体开始时间、结束时间、英文、中文和完成状态。媒体时间以秒为单位，识别结果返回时沿用原请求的时间范围。

字幕窗口为该短语的媒体起止范围。结果提前完成时留在队列；播放进入窗口后显示；离开窗口后清除。后续如需延长阅读时间，必须限制在下一条字幕之前，并单独验收。

| 结果到达时机 | 画面字幕行为 |
| --- | --- |
| 对应短语还未播放 | 排队等待，不提前显示 |
| 对应短语正在播放 | 立即显示可用版本；中文晚到时补入同一条 |
| 对应短语已经结束 | 只补全字幕记录，不把过期字幕插入后续画面 |
| 新版本先于旧版本返回 | 保留新版本，拒绝旧结果覆盖 |
| 属于已切换频道或已跳转的旧时间线 | 丢弃结果，不进入当前画面或当前会话记录 |

默认双语模式下，中文未完成可先显示对应英文；仅中文模式下则暂时留空，不擅自改变用户选择。字幕记录也在对应内容开始播放后再对用户显示，避免提前泄露内容。

### 4.4 积压与失败

识别、翻译队列必须有容量和时间范围上限。同一短语的待处理旧版本可合并；优先处理仍有机会赶上播放窗口的任务，过期积压允许跳过，并记录跳过数量。不能让历史翻译持续阻塞当前字幕。

翻译失败不改变媒体播放速度或延迟。显示一次明确状态，保留可用英文；恢复字幕处理时从当前有效窗口接续，不重放过期积压。模型未就绪时媒体按缓冲条件开始播放，状态说明“字幕模型准备中”，不能为模型下载无限等待。

## 5. 交互与边界

| 场景 | 约定行为 |
| --- | --- |
| 切台、切换来源 | 清除旧字幕和任务，开启新会话并重新建立约 3 秒缓冲 |
| 首次缓冲 | 允许识别提前运行，不能被现有 `video.paused` 判断误拦截 |
| 用户暂停录播 | 播放与字幕时间冻结；处理最多完成有限的提前窗口，不无限读入 |
| 恢复录播 | 使用保留缓冲继续播放，不机械重复等待 3 秒 |
| 用户暂停直播 | 暂停期间不无限缓存；恢复时首期回到新的直播缓冲起点并清空旧时间线，界面明确提示回到直播 |
| 录播跳转 | 取消旧任务，在目标位置重建缓冲；旧结果不得串入 |
| 网络卡顿 | 字幕跟随停止的媒体时钟；恢复后复核时间线，实际发生跳转或断续时重建代次 |
| 录播末尾不足 3 秒 | 用剩余媒体完成播放，排空对应字幕，不无限等待不足的缓冲 |
| 关闭字幕 | 停止识别和翻译，保持当前媒体播放位置与缓冲，不突然向前跳 |
| 重新开启字幕 | 利用现有媒体缓冲重新建立处理窗口，不中断原声 |
| 全屏 | 沿用同一字幕队列和播放时钟，与窗口模式一致 |

首期覆盖当前可访问、可解码音轨的 HLS 直播与 HLS 录播。普通本地视频、其他录播格式及 Chrome/YouTube 扩展不自动视为已支持。依赖播放时音频采集的后备路径无法仅靠延后播放获得提前识别能力，须验证可预读音轨，否则明确标记该路径不支持此模式。

## 6. 实施范围与顺序

0. **设置入口与默认隔离**：新增默认关闭的字幕缓冲开关和 3／4／5 秒选项；保存偏好；不开启时保持当前播放和字幕路径。播放中更改设置在下次载入来源或用户主动重新载入后生效，明确提示，避免立即跳帧或重复播放。
1. **媒体时间基础**：在音频输出、分段和任务关联中保留时间范围与代次；确认分片切换、重复片段和 HLS 时间线断续的映射。
2. **缓冲与提前读取**：分离启动缓冲、用户暂停和正常播放；实现约 3 秒音视频缓冲与识别提前读取，检查直播自动追赶行为。
3. **字幕调度**：识别完成不直接显示；新增按媒体时间调度的队列、过期规则和版本检查；字幕历史与导出沿用同一记录。
4. **短语与预算**：调整分段和队列优先级，使用真实长句与停顿语音验证可读性、及时率和资源占用。
5. **状态与验收**：通过现有原生桥接呈现准备、播放及字幕落后状态；完成下述场景，再决定是否打包。

主要修改候选为 `public/hls-audio.js`、`public/speech-chunks.js`、`public/app.js`、`public/captions.js`；原生桥接及状态展示按实际需要调整。现有识别和翻译接口优先复用，只有测量证明必要时才扩展。实施前保留当前可用版本；不借此更换模型、重写播放器或改造整体外观；底部控件和字幕侧栏范围见第 10、11 节，全屏与悬浮小窗保持现状。

## 7. 验收标准

下列是未来实施后的验证要求，不是本次已完成的测试。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 默认模式回归 | 首次启动不开启新增缓冲；识别、翻译和播放保持现有方式；设置保存及重启恢复正确 |
| 3／4／5 秒选项 | 分别验证所选值实际生效；播放中修改只影响下一次载入，有明确提示 |
| 时间标记测试媒体 | 正常网络、模型已就绪时，相对相同来源的无新增缓冲基线，新增延迟目标为 3 秒；初始验收容差暂定 ±0.5 秒，记录实际偏差 |
| 原声与画面同步 | 同一播放器输出，使用音画标记核对；相对原版本不新增可测的同步偏差 |
| 可控快速识别与翻译 | 提前得到的字幕不会提前显示，到对应媒体窗口才出现 |
| 可控慢翻译与乱序返回 | 媒体不中断；窗口内晚到可补，过期仅补记录，旧版本不覆盖新版本 |
| 连续讲话超过 16 秒 | 有连续短语字幕，不等待整段结束；不出现未来短语提前上屏 |
| 暂停、恢复、跳转、切台 | 没有串台、旧句回闪或暂停时字幕自行消失；恢复行为符合第 5 节 |
| 网络卡顿与时间线断续 | 字幕不依墙钟跑到画面前面；恢复后对齐当前时间线 |
| 模型未准备好或翻译失败 | 仅字幕状态受影响；不额外等待字幕完成才播放 |
| 录播结尾与全屏 | 尾段能结束，不因不足 3 秒卡住；全屏字幕行为一致 |
| 连续运行至少 30 分钟 | 内存与队列保持有界，新增延迟不因字幕积压持续增长 |

验收至少记录：实际缓冲时长、识别读取提前量、分段等待、识别和翻译耗时、字幕在窗口开始前就绪的比例、窗口内晚到比例、过期比例及队列峰值。模型耗时记录中位数与 P95；真实语音抽查人名、数字、长句和断句完整性。性能比例以实测报告为准，本方案不预先承诺提升幅度。

## 8. 完成定义

默认播放方式保持现状；可选 3／4／5 秒缓冲模式在当前原生应用实际播放中可观察；画面和原声同步、连续；识别确实处理播放位置前方的音频；字幕按媒体时间展示且不会串句、提前或被过期结果覆盖。最终交付需附运行证据、实际延迟和字幕及时率，以及尚不支持的来源类型。

当前仅完成方案。尚未证明现有硬件和模型在 3 秒窗口内能达到何种翻译及时率，也未改变现有应用行为。


## 9. 第二项：全屏与悬浮小窗（用户确认已有）

用户最新确认：“第二个有了，没问题了。”因此移除上一版对此项新增、改位和重新设计的要求，沿用已有功能。本次不为此项新增实现任务，也不把之前建议的小窗尺寸或关闭方式当作已确认需求。

## 10. 第三项：底部状态栏与按钮闲置时收起

### 用户要求

底部显示播放状态、时间的区域，与播放／暂停、字幕等按钮一起，在不操作窗口时缩小，减少对画面的占用；重新操作时恢复。

### 建议交互（初始参数，待实际体验验收）

- 正常播放中连续约 3 秒没有鼠标或键盘操作，底部整体平滑收为低存在感的紧凑条；状态文字和时间折叠，播放／暂停、字幕等按钮同步收起。
- 不只是把文字和图标按比例缩成难以点击的小按钮。紧凑态保留清楚的唤回区域，鼠标移动或键盘操作即可恢复完整控件；恢复动作不触发播放或字幕切换。
- 指针停留在底部控件上、键盘焦点位于控件内、正在拖动或菜单打开时不自动收起。用户暂停时保留展开控件，方便继续操作。
- 收起和展开只改变控件呈现，不暂停播放、不改变缓冲模式、不清除字幕。字幕层始终保持可读，不随控件缩小，也不被紧凑条遮住。
- 避免反复重排视频画面导致尺寸跳动；普通窗口和全屏保持一致的收起逻辑。悬浮小窗沿用现有能力，仅做必要的兼容核对。
- 字幕回看侧栏中正在滚动或选择文字，属于用户仍在操作；不得把正在使用的侧栏一起收起。

### 验收

播放时静置、移动鼠标、停留控件、键盘聚焦、暂停、打开菜单分别验证。状态与按钮同步收起和恢复，没有误触、音画跳动、字幕遮挡或无法唤回。约 3 秒为初始闲置阈值，与可选字幕缓冲的 3～5 秒是两个独立参数。

## 11. 第四项：字幕回看侧栏

### 用户要求

从字幕按钮进入侧边栏，像查看会议逐字记录一样，向上滚动查看之前的字幕，同时继续观看当前播放内容。

这里的“回看”首先指文字历史阅读，不包含自动生成会议总结，也不要求点击字幕跳转视频或提供直播回放。

### 入口与布局

- 保留字幕开启／关闭能力。建议将现有字幕按钮做成主按钮加附属菜单：主按钮打开／关闭回看侧栏；附属菜单提供字幕开启／关闭及原有语言显示选择，明确区分“关闭侧栏”和“关闭字幕”。
- 侧栏默认在窗口右侧展开，可关闭；主画面继续播放。宽度需兼顾视频和中英文阅读，窄窗口采用可关闭的覆盖式侧栏，不能将视频挤到不可用。
- 侧栏以时间顺序从旧到新排列，最新记录在底部；向上滚动即可查看更早内容。每条展示时间、原文和译文，按短语／句子合并增量结果，不把每次修订重复列成新记录。
- 支持选择和复制文字；复用现有导出能力，不要求在本次新增总结、搜索或云同步。

### 滚动与持续更新

- 首次打开定位到最新记录。用户停留底部时，新字幕自动跟随。
- 用户向上滚动后停止自动跟随；新字幕和迟到翻译继续更新数据，但不能强制把阅读位置拉回底部。
- 离开底部时显示“回到最新”入口及新内容提示；点击后恢复自动跟随。历史译文补全导致高度变化时，应保持正在阅读条目的视觉位置。
- 关闭再打开时尽量保留本次阅读位置与跟随状态。开关侧栏不停止识别、不重启播放、不清空历史。
- 启用缓冲模式时，尚未播放到的预处理字幕不提前进入可见历史；过期译文可以补入已经播放过的对应条目。
- 关闭字幕后保留已产生记录可读，不继续生成新记录；切换来源时按会话分组标识来源，旧任务不能写入新来源记录。

### 现有基础与保留范围

本次查阅源码发现已有 `PlayerModel.history`、字幕导出及设置页“字幕记录”区域；设置页目前使用 `history.suffix(20)`，底层 `CaptionView` 最多保留 120 条。新侧栏应复用现有数据来源，但不能简单照搬仅展示 20 条的设置页。

首期方案保留本次运行最近 120 条的有界记录，并在侧栏明确标注这一范围；不足以代表整场节目完整存档。到达上限淘汰旧记录时，保持仍存在的阅读条目位置；若正在阅读的条目被淘汰，则提示“更早记录已清理”。退出后不持久保存，沿用当前隐私与记录策略。完整长场次存档可单独扩展，不在本次默认新增。

### 修改候选与验收

主要复用 `native/PlayerViews.swift`、`native/PlayerModel.swift` 与 `public/native-bridge.js` 的状态和记录链路；必要时补齐 `public/captions.js` 的会话与条目标识。默认播放模式也必须支持侧栏，不能依赖开启缓冲模式。

验收至少覆盖：打开／关闭侧栏不中断播放；向上滚动时新字幕不抢位置；回到最新后持续跟随；迟到翻译原位更新且无重复；文字可复制、记录可导出；关闭字幕后旧记录仍可读；切换来源不混淆；120 条上限与清理提示正确；全屏及窄窗口可用；底栏收起不干扰侧栏阅读。
